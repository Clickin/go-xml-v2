# stax-xml asset comparison on Windows amd64

Reference: `Clickin/stax-xml` commit `07cca8a0f53f83a47de4149f84749e4259dc9360`, specifically `packages/benchmark/assets` and `packages/benchmark/reader-cross-runtime.mjs`. The eight selected checked-out asset files and their SHA-256 hashes are recorded in `assets.csv`. `mini-sample`, `sample`, `complex`, and `books` exercise small record documents, empty elements and CDATA; `ptest` exercises namespace prefixes and CDATA; `crlf` exercises line endings and a DOCTYPE; `midsize` and `large` are the reference 13 MiB and 100 MiB record corpora. Invalid and malformed assets were excluded from throughput measurements.

Go source revision `bd5149100704087efd1edf06bfb7d6956aa636ac`, Go 1.28 devel `GOEXPERIMENT=xmlv2`, `GOAMD64=v1`, `CGO_ENABLED=0`, `GOMAXPROCS=8`; Woodstox 7.2.0 and StAX2 4.3.0 on Temurin Java 25.0.1 with `-Xms512m -Xmx512m`; quick-xml 0.42.0 compiled release with Rust 1.99.0. CPU: Intel Core i5-13600K. Runs are single-threaded and serial; filesystem cache is not flushed.

The measured operation includes reading the file and parsing it, coalescing adjacent text/CDATA, trimming text, and folding start/end qualified names, non-namespace attribute names and resolved values, and nonempty text into a 32-bit checksum using the reference fold/mix method. All implementations produce identical event counts and checksums for each timed asset. Namespace declarations are consistently excluded from the attribute count and checksum: unlike StAX, Go and quick-xml expose them as attributes. This is an explicit adaptation of the upstream comparison contract, which is intended for its generated ASCII catalog; the upstream Rust example does not fully handle empty tags, decoded entity references, or Unicode checksum semantics. A separate check containing a prefixed namespace, escaped attribute, numeric and named entities, Korean text, an emoji, CDATA, and an empty tag gave 7 events and checksum -1974645466 for all three. This checksum is not a full proof of semantic equivalence. DTD processing is disabled in Woodstox and custom DTD entities are outside this workload. quick-xml and the other parsers have different validation and namespace semantics.

For assets smaller than 1 MiB, each measured sample is the average of 100 consecutive full file-read-and-parse operations; there are four warmup batches and nine samples per implementation. Larger assets use one operation per sample: nine samples after four warmups for midsize and five after two warmups for large. The 100-operation batches avoid coarse clock resolution for tiny Go runs. `samples.csv` has the individual batch averages; `summary.csv` reports the median and observed range. Samples share a single process per implementation, run in fixed Go/Woodstox/quick-xml order, so they are not independent and the range is not a confidence interval. No allocation or cold-cache measurement is included. Results should not be directly compared with the preceding in-memory length-sum benchmark, which did different work.

To reproduce, clone the specified stax-xml revision to `pkg/stax-xml-reference`, build this tree's Go toolchain, and build `main.go` to `pkg/asset-go.exe` with `GOEXPERIMENT=xmlv2`, `GO111MODULE=off`, `CGO_ENABLED=0` and the repository `bin/go.exe`. Compile `AssetBench.java` with the Woodstox and StAX2 jars into `pkg/asset-java`; compile `rust/` using `cargo build --release --locked` with `CARGO_TARGET_DIR` set to `pkg/asset-target`. Adjust the jar paths in `run.ps1` if necessary, then run it from the repository root. It overwrites the CSVs and aborts if any event count or checksum differs.

Measured with LF assets and an allocation-free Go checksum harness from commit `7e487b46c4`; earlier CRLF results are invalid. The LF midsize and large assets are 13,584,398 and 101,882,907 bytes, respectively.
